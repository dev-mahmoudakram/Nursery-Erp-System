# نظام إدارة المشاتل - غصن التنمية (Nursery ERP)

## هذا مشروع Laravel كامل وقابل للتشغيل فعليًا
هذا **ليس سكفولد جزئي** — المجلد يحتوي على كل ملفات Laravel القياسية (`composer.json`, `artisan`,
`bootstrap/app.php`, `config/*`) بالإضافة لكل الكود المخصَّص (Models/Controllers/Views/Migrations)
للموديولات السبعة. كل ما تحتاجه هو تثبيت الحزم وإعداد قاعدة البيانات.

## طريقة التشغيل
```bash
cd nursery-erp-system-code

composer install

cp .env.example .env
php artisan key:generate

# عدّل .env بإعدادات قاعدة بياناتك (افتراضيًا MySQL، اسم القاعدة nursery_erp):
# DB_DATABASE=nursery_erp
# DB_USERNAME=root
# DB_PASSWORD=...

# أنشئ قاعدة البيانات فعليًا أولًا (مثال):
# mysql -u root -p -e "CREATE DATABASE nursery_erp CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

php artisan migrate --seed
php artisan storage:link
php artisan serve
```

بعدها افتح `http://localhost:8000` — هتحوَّل تلقائيًا لصفحة تسجيل الدخول.

**بيانات الدخول الافتراضية (من الـ Seeder):**
- البريد: `admin@nursery-erp.test`
- كلمة المرور: `password`
- **غيّرها فورًا في أي بيئة حقيقية.**

## ما الذي تغيَّر عن الإصدار السابق
كانت النسخة الأولى تتطلب منك تشغيل `composer create-project` ونسخ الملفات يدويًا فوقها — وهذا تسبب في
حزمة غير مكتملة (بلا `composer.json` ولا `artisan` ولا `bootstrap/`). هذه النسخة الحالية تحمّل هيكل
Laravel 11 الرسمي كاملًا من GitHub مباشرة، ثم تدمج فيه كل الكود المخصَّص وتربطه (`bootstrap/app.php`,
`config/auth.php`, `routes/console.php`) — **جاهزة لأمر `composer install` مباشرة دون أي نسخ يدوي**.



## الجداول المُنشأة في هذا الموديول
- `nurseries` — المشاتل (٨ مشاتل)
- `locations` — المواقع الهرمية (منطقة/قطاع/صف/حوض/موقع داخلي) + مواقع الحالة (تحت الفحص، تالف، معزول...)
- `item_categories` — الفئات الرئيسية والفرعية
- `items` — بطاقة الصنف الكاملة (كل الحقول المذكورة في كراسة الطلب بند ٥.٢، بما فيها ٦ قوائم أسعار)
- `batches` — الدفعات (المستوى الأول لإدارة النبات - بند ٥.٣)
- `individual_units` — الوحدة المنفردة للأشجار مرتفعة القيمة (المستوى الثاني - بند ٥.٣)
- `status_histories` — سجل تدقيق كامل لكل تغيّر حالة (polymorphic، يخدم batches و individual_units)
- `inventory_movements` — كل حركات المخزون (استلام، تحويل، حجز، فك حجز، جرد بأنواعه، تلف، إتلاف) + `client_uuid` للمزامنة الآمنة من الجوال
- `nursery_transfers` + `nursery_transfer_items` — دورة التحويل الكاملة بين المشاتل (بند ٥.٧) بحالات:
  requested → approved → preparing → in_transit → received → inspected → closed

## API (للجوال والتكاملات)
`routes/api.php` بنقاط نهاية JSON لنفس الموديول، أبرزها:
- `GET /api/v1/batches/qr/{qr}` — البحث عن دفعة برمز QR (للمسح الميداني)
- `POST /api/v1/inventory-movements/sync` — مزامنة حركات مُلتقطة أثناء انقطاع الاتصال (Idempotent عبر client_uuid)
- `POST /api/v1/batches/{batch}/status` — تغيير حالة دورة الحياة

التفاصيل الكاملة (أمثلة الطلب/الاستجابة) في وثيقة **09 - API Documentation**.

## الدعم الثنائي اللغة (عربي/إنجليزي) ✅ مُفعَّل فعليًا
كل الشاشات (تخطيط الصفحة، القوائم، النماذج، رسائل النجاح) تتغيّر حسب اللغة، بما في ذلك اتجاه الصفحة RTL/LTR:

1. ملفات الترجمة: `lang/ar/messages.php` و `lang/en/messages.php` (كل نصوص الواجهة).
2. `app/Http/Middleware/SetLocale.php` يقرأ اللغة من الجلسة ويضبط `app()->setLocale()`.
3. مسار التبديل: `GET /lang/{ar|en}` — زرّا **AR/EN** ظاهران في الشريط العلوي بكل شاشة.
4. ✅ **Middleware مُسجَّل بالفعل** في `bootstrap/app.php` — لا حاجة لأي خطوة يدوية.
5. عمودا `name_en` في `nurseries` و`items` مستخدَمان بالفعل: الواجهة تعرض `name_en` تلقائيًا عند اختيار الإنجليزية (وتتراجع للعربي إن كان فارغًا) — نفس المبدأ يُطبَّق على أي جدول جديد بإضافة عمود `_en` مقابل.
6. لترجمة رسائل التحقق الافتراضية (Validation) أيضًا: نفّذ `php artisan lang:publish` بعد التثبيت، ثم عدّل `lang/en/validation.php` و`lang/ar/validation.php` حسب الحاجة.

## موديول ٢: CRM والمبيعات (Customers → Opportunities → Quotations → Sales Orders → Invoices)

جداول جديدة: `customers`, `sales_opportunities`, `quotations` + `quotation_items`, `sales_orders` + `sales_order_items`, `invoices`, `payments`.

منطق أعمال حقيقي مطبَّق (وليس توثيقًا فقط):
- **التسعير التلقائي**: `Item::priceFor($customerType)` يُستدعى تلقائيًا عند إنشاء عرض السعر حسب نوع العميل (retail/wholesale/contractor/project/government) — BR-CRM-03.
- **الحجز الفوري**: `Quotation::reserveStock()` يزيد `batches.reserved_quantity` ويسجل حركة `reserve` عند إنشاء العرض — BR-CRM-04 / FR-031.
- **فك الحجز التلقائي**: أمر Artisan `quotations:unreserve-expired` (انظر `app/Console/Commands/UnreserveExpiredQuotations.php`) يفك حجز العروض المنتهية دون قبول. ✅ **مجدوَل بالفعل** كل ساعة في `routes/console.php`. شغّل `php artisan schedule:work` محليًا، أو Cron على `php artisan schedule:run` كل دقيقة في الإنتاج.
- **الخصم النهائي عند التسليم فقط**: `SalesOrder::markItemDelivered()` يخصم `quantity` و`reserved_quantity` معًا فقط عند تسجيل تسليم فعلي، تطبيقًا لمبدأ BP-04 — لا خصم نهائي عند مجرد إنشاء الطلب.
- **الفوترة والتحصيل**: `Invoice::createFromOrder()` و`Invoice::recordPayment()` يحدّثان تلقائيًا `customers.current_balance` (لمتابعة حد الائتمان BR-B2B-01).
- **إلزام سبب الخسارة**: `OpportunityController::updateStage()` يرفض الحفظ إذا `stage=lost` بدون `lost_reason` — FR-030.

هذا الموديول **ثنائي اللغة بنفس أسلوب الموديول الأول** (كل النصوص عبر `__('messages....')`، ومفاتيح الترجمة مضافة بالكامل في `lang/ar/messages.php` و`lang/en/messages.php`).

### ما لم يُبنَ بعد من هذا الموديول
- شاشة مصفوفة اعتماد صريحة عند تجاوز هامش الربح للحد الأدنى (BR-PRC-02) — الحقل `margin_percent` محسوب ومعروض، لكن منطق الرفض/الاعتماد غير مُفعَّل بعد.
- توليد PDF فعلي لعرض السعر بنسختيه العربية والإنجليزية (BR-CRM-04) — البيانات جاهزة، التصدير غير مُنفَّذ.
- تنبيهات BR-ALT-01 (تجاوز حد الائتمان، تأخر تحصيل) — البيانات (current_balance, due_date) موجودة وجاهزة لبناء التنبيهات عليها.

## موديول ٣: المشتريات والموردون (Suppliers → Purchase Requests → Purchase Orders → Goods Receipts)

جداول جديدة: `suppliers`, `purchase_requests`, `purchase_orders` + `purchase_order_items`, `goods_receipts` + `goods_receipt_items`.

منطق أعمال حقيقي مطبَّق:
- **دورة الطلب**: طلب شراء (pending) → اعتماد/رفض → تحويل لأمر شراء فعلي (`PurchaseRequestController::approve/reject`).
- **الاستلام الفعلي ينشئ مخزونًا تلقائيًا**: `GoodsReceipt::receive()` — لكل بند مُستلَم بجودة سليمة، يُنشئ **دفعة (Batch) جديدة** فعليًا في مشتل الوجهة، ويسجل حركة `receive`، ويربط التكلفة الفعلية — هذا يغذّي مباشرة موديول المخزون المبني مسبقًا (BR-PUR-01، وربط تكلفة الشراء بالمخزون).
- **استلام جزئي مدعوم بالكامل**: كل بند بأمر الشراء يتتبع `received_quantity` مستقلة، وحالة الأمر (`sent/partially_received/received`) تُحدَّث تلقائيًا عبر `PurchaseOrder::refreshStatusFromReceipts()`.
- **فحص الجودة عند الاستلام**: أي بند يُعلَّم `quality_ok=false` يُغلَق إداريًا (يُحتسب مُستلَمًا) لكن **لا يُنشئ دفعة مخزون** — أي لا يدخل للمخزون بضاعة غير مطابقة.

ثنائي اللغة بنفس الأسلوب.

### ما لم يُبنَ بعد من هذا الموديول
- مقارنة عروض أسعار الموردين قبل اختيار المورد (البند مذكور في BRD لكن غير مُنفَّذ كشاشة).
- تحديث تلقائي لتقييم المورد (`suppliers.rating`) بناءً على الالتزام بالمواعيد والجودة — الحقل موجود، التحديث التلقائي غير مُفعَّل.

## موديول ٤: النقل والتجهيز والتسليم (Vehicles/Drivers → Delivery Orders → Proof of Delivery)

جداول جديدة: `vehicles`, `drivers`, `delivery_orders` + `delivery_order_items`.

منطق أعمال حقيقي مطبَّق:
- **جدولة تسليم من أمر بيع مباشرة**: زر 🚚 داخل صفحة أمر البيع ينشئ أمر تسليم مرتبط ببنود مُحدَّدة وكمياتها (قد لا تغطي أمر التسليم الواحد كل بنود الطلب — تسليمات جزئية متعددة مدعومة).
- **تخصيص مركبة/سائق**: عند التخصيص تتغيّر حالتهما تلقائيًا إلى `in_use`/`on_route`، وتعود لـ `available` تلقائيًا عند تأكيد التسليم أو فشله.
- **الخصم النهائي من المخزون يحدث هنا فعليًا**: `DeliveryOrder::confirmDelivery()` يستدعي نفس `SalesOrder::markItemDelivered()` المبني في موديول CRM لكل بند — هذا يوحّد نقطة الخصم النهائي الوحيدة في النظام كله (BP-04 خطوة 6 / BR-LOG-02).
- **إثبات التسليم**: اسم المستلم إلزامي عند التأكيد؛ الحقول `proof_photo_path` و`proof_signature_path` جاهزة لاستقبال رفع صورة/توقيع فعلي (رفع الملفات نفسه غير مُنفَّذ بعد في الواجهة).
- **فشل/رفض التسليم**: `DeliveryOrder::markFailed()` يسجل السبب **دون** خصم أي مخزون — الكمية تبقى محجوزة على أمر البيع لإعادة جدولة تسليم لاحق.

ثنائي اللغة بنفس الأسلوب.

### ما لم يُبنَ بعد من هذا الموديول
- رفع فعلي لصورة/توقيع الإثبات (multipart upload) — الأعمدة جاهزة في قاعدة البيانات فقط.
- تخطيط خط سير (Route Planning) لعدة تسليمات في رحلة واحدة.
- مؤشر نسبة التسليم في الموعد وبالكامل (BR-LOG-03) — البيانات الخام (scheduled_date, delivered_at) موجودة وجاهزة لبناء هذا التقرير.

## موديول ٥: B2B (عقود خاصة + بوابة عميل مستقلة)

جداول جديدة: `b2b_contracts` + `b2b_contract_items`, `customer_portal_users` (Guard منفصل تمامًا عن مستخدمي النظام الداخليين).

منطق أعمال حقيقي مطبَّق:
- **أسعار تعاقدية تتفوق على القوائم الست القياسية**: `Customer::activeContract()->contractPriceFor($itemId)` يُستدعى أولًا في `QuotationController::store()` وفي `PortalController::reorder()` قبل الرجوع لـ `Item::priceFor()` — BR-B2B-01.
- **فحص حد ائتمان فعلي عند تأكيد الطلب**: `QuotationController::accept()` يرفض تحويل العرض لأمر بيع إذا (الرصيد الحالي + قيمة الطلب) تجاوز الحد التعاقدي أو حد العميل العام — BR-ALT-01.
- **بوابة عميل مستقلة بالكامل**: Guard خاص باسم `customer` ✅ **مُسجَّل بالفعل في `config/auth.php`** بحيث لا يمكن لعميل الوصول لأي شاشة إدارية داخلية إطلاقًا، والعكس صحيح — BR-B2B-02.
- **إعادة الطلب (Reorder)**: عميل يضغط زر واحد في لوحته فينسخ بنود أي أمر بيع سابق إلى **عرض سعر جديد كمسودة** بالأسعار الحالية (تعاقدية إن وُجدت)، يراجعه قبل أي تأكيد — BR-B2B-02.

**ملف مسارات منفصل** (`routes/portal.php`) لعزل مسارات العميل تمامًا عن `routes/web.php` الإداري — ✅ **مُسجَّل بالفعل** عبر `then:` closure في `bootstrap/app.php`.

ثنائي اللغة بالكامل (تسجيل الدخول ولوحة العميل بتصميم مستقل عن الشاشات الإدارية، لأن العميل الخارجي لا يحتاج القائمة الجانبية الإدارية).

### ما لم يُبنَ بعد من هذا الموديول
- استيراد طلبات B2B بأصناف متعددة عبر ملف (BR-B2B-02) — الإدخال حاليًا عبر الشاشة العادية لعرض السعر فقط.
- تقارير ربحية حسب العميل/المشروع ومستهدف بيعي لكل عميل أو مندوب (BR-B2B-03) — تُبنى لاحقًا ضمن موديول التقارير العام.
- شاشة إدارية لإنشاء حسابات `customer_portal_users` (حاليًا تُنشأ يدويًا عبر Tinker/Seeder إلى حين بناء الشاشة).

## موديول ٦: B2G (المنافسات الحكومية)

جداول جديدة: `government_tenders`, `tender_evaluations`, `tender_documents`.

منطق أعمال حقيقي مطبَّق (يطابق دورة BP-05 الموثَّقة في وثيقة BPMN بالكامل):
- **تقييم قرار الدخول**: `TenderEvaluation::computeSystemRecommendation()` يحسب توصية آلية أولية (bid/no_bid) بناءً على حد أدنى: هامش ربح ≥ ١٥٪، مخاطر ليست مرتفعة، وقدرة تشغيلية/توافق نشاط ≥ ٣ من ٥ — BR-B2G-02.
- **القرار النهائي دائمًا بيد الإدارة العليا**: التوصية الآلية إشارة داعمة فقط؛ `GovernmentTenderController::decide()` يسجل القرار الفعلي (`final_decision`) بشكل منفصل تمامًا عن التوصية، ولا يُقفل الأمر تلقائيًا بمجرد التوصية.
- **دورة الحالة الكاملة**: evaluating → (decided_no_bid | preparing_offer) → submitted → (won | lost) — مطابقة لـ BP-05.
- **إلزام سبب النتيجة**: لا يمكن تسجيل فوز أو خسارة دون `outcome_reason` — للتعلم المؤسسي من كل منافسة.

ثنائي اللغة بنفس الأسلوب.

### ما لم يُبنَ بعد من هذا الموديول
- ربط فعلي بين المنافسة وعرض سعر حقيقي (`quotation_id` موجود في الجدول لكن شاشة الربط/الإنشاء التلقائي للعرض الفني والمالي غير مُنفَّذة بعد — يمكن استخدام موديول CRM الحالي يدويًا لإنشاء العرض ثم ربط رقمه لاحقًا عبر قاعدة البيانات مباشرة إلى حين بناء الشاشة).
- رفع فعلي لمستندات المنافسة (`tender_documents.file_path` جاهز، رفع الملفات نفسه غير مُنفَّذ في الواجهة).
- إدارة فرص التوريد للمقاولين الفائزين بمشروعات حكومية بشكل منفصل عن المنافسات المباشرة (BR-B2G-03).

## موديول ٧: B2C (المتجر الإلكتروني العام)

جداول جديدة: `storefront_products`, `carts`+`cart_items`, `coupons`, `online_orders`+`online_order_items`, `product_reviews`.

هذا الموديول مختلف عن كل ما سبق: واجهته **عامة بالكامل بدون تسجيل دخول** (Guest)، وله تخطيط بصري مستقل (`resources/views/storefront/*`) عن الشاشات الإدارية.

منطق أعمال حقيقي مطبَّق:
- **نشر مُنسَّق يدويًا فقط**: أي صنف لا يظهر بالمتجر إلا بعد نشر صريح من موظف (`StorefrontProduct.is_published`) — يطبّق حرفيًا بند BR-B2C-04 (١٠٠-٢٠٠ صنف موثوق فقط)، وليس عرضًا تلقائيًا لكل الكتالوج.
- **مخزون حي وليس رقمًا مخزَّنًا**: `StorefrontProduct::getLiveStockAttribute()` يجمع `available_quantity` الفعلي من كل الدفعات الجاهزة للبيع لحظيًا؛ أي صنف نفد يختفي من القائمة العامة تلقائيًا دون تدخل يدوي.
- **سلة ضيف بدون حساب**: عبر كوكيز (`session_token`) فقط — BR-B2C-02.
- **أهم نقطة تكامل في المشروع كله**: `OnlineOrder::convertToInternalOrder()` — عند تأكيد الموظف لطلب متجر، يُنشئ عرض سعر حقيقي، يخصص دفعات فعلية FIFO حسب تاريخ الإنتاج بمشتل الوجهة، **يحجز المخزون بنفس محرك CRM بالضبط**، ثم يحوّله لأمر بيع حقيقي — طلب المتجر العام يمر بنفس ضوابط الجودة والمخزون المطبَّقة على كل قناة أخرى، دون أي مسار موازٍ أو مختصر.
- **كوبونات خصم حقيقية**: تحقق من الصلاحية الزمنية وحد الاستخدام قبل التطبيق (`Coupon::isValidNow()`).
- **تقييمات تحت المراجعة إلزاميًا**: أي تقييم عام لا يظهر (`is_approved=false`) حتى تعتمده الإدارة.

**ملف مسارات منفصل تمامًا** (`routes/storefront.php`, بادئة `/shop`) — بلا أي Guard أو Middleware مصادقة، لأنه عام بتصميم.

### ما لم يُبنَ بعد من هذا الموديول
- تكامل واتساب فعلي للإشعارات (BR-B2C-03) — يمكن ربطه لاحقًا كخدمة Notification مستقلة تُستدعى بعد `convertToInternalOrder()`.
- بوابة دفع إلكتروني فعلية (`payment_status` محدَّث يدويًا الآن عند طلب COD أو يُفترض 'paid' فورًا عند الدفع الإلكتروني — التكامل الحقيقي مع بوابة دفع سعودية مثل مدى/Tap غير مُنفَّذ).
- معالجة مرتجعات المتجر (`status=returned` موجودة كحالة لكن بلا شاشة عمل).

## RBAC فعلي بالكود (وليس توثيقًا فقط)

- عمود `role` على جدول `users` (migration `2025_01_08_000001`) بخمس قيم مطابقة لمصفوفة Security & Infrastructure: `admin`, `nursery_manager`, `inventory_keeper`, `sales_rep`, `accountant`.
- `App\Support\Role` يجمع الثوابت ومجموعات الأدوار المسموحة لكل فئة إجراء.
- `App\Http\Middleware\EnsureUserHasRole` يرفض أي طلب بكود **403 فعلي** إن لم يكن دور المستخدم ضمن القائمة المطلوبة — جرّبه بنفسك: أنشئ مستخدم `sales_rep` وحاول فتح `items.create` مباشرة، سيُرفض.
- ✅ **Middleware مُسجَّل بالفعل** (alias `role`) في `bootstrap/app.php`.
- `routes/web.php` بالكامل الآن داخل `Route::middleware(['auth'])` مع مجموعات فرعية `role:...` لكل إجراء حسّاس (تعديل الأصناف/الأسعار = admin فقط، التحصيل المالي = admin/accountant فقط، قرار الدخول في منافسة B2G = admin فقط... إلخ) — طابِق كل مجموعة بجدول المصفوفة في وثيقة ١١.
- `app/Models/User.php` مُرفَق بدوال `hasRole()` و`isAdmin()` — هو نفسه ملف User الفعلي في المشروع (تم استبداله بالكامل، لا حاجة لأي دمج).
- **قيد معروف**: لا يوجد بعد تقييد "مدير/أمين المشتل بمشتله فقط" (عمود `users.nursery_id` موجود وجاهز لذلك، لكن الفلترة الفعلية في الاستعلامات غير مُطبَّقة بعد).

## رفع ملفات فعلي (وليس أعمدة فارغة فقط)

ثلاث نقاط تكامل فعلية مُنفَّذة كنموذج يُكرَّر بنفس الأسلوب على بقية الحقول المشابهة:
- **إثبات التسليم**: صورة + توقيع فعليين يُرفعان عند تأكيد أي تسليم (`DeliveryOrderController::confirm`)، ويُعرضان في صفحة التسليم بعد التأكيد.
- **صورة غلاف منتج المتجر**: تُرفع عند نشر أي صنف في B2C (`StorefrontProductController::store`).
- **مستندات المنافسات الحكومية**: رفع متعدد لأي عدد من المستندات لكل منافسة (`GovernmentTenderController::uploadDocument`).

**ملاحظة**: `php artisan storage:link` مذكور بالفعل في خطوات التثبيت أعلى الملف — لازم لعرض الملفات المرفوعة من `storage/app/public` عبر `public/storage`.

**الحقول المتبقية غير المُفعَّلة**: صور الأصناف (`items.image_path`)، صور الدفعات أثناء الجرد (`batches.image_path`)، صور حركات الجرد (`inventory_movements.photo_path`) — الأعمدة جاهزة، ونفس نمط الكود أعلاه يُطبَّق عليها مباشرة عند الحاجة.

## رفع صور الأصناف والدفعات (تحديث)

نفس نمط رفع الملفات المُطبَّق سابقًا (إثبات التسليم، غلاف منتج المتجر، مستندات المنافسات) طُبِّق الآن على آخر حقلين متبقيين:
- **صورة الصنف**: تُرفع عند إضافة/تعديل أي صنف (`ItemController`)، وتظهر كصورة مصغَّرة في قائمة الأصناف.
- **صورة الدفعة**: تُرفع اختياريًا عند إنشاء الدفعة، **وقابلة للتحديث لاحقًا في أي وقت** من صفحة تفاصيل الدفعة (`BatchController::uploadPhoto`) — مفيد عمليًا أثناء الفحص الدوري أو توثيق حالة تلف.

بهذا تُغطَّى كل حقول الصور المخطَّط لها في قاعدة البيانات بمنطق رفع فعلي، ولا يوجد أي عمود `image_path`/`photo_path`/`proof_*` متبقٍّ بلا تنفيذ.

**ملاحظة نهائية**: بناءً على توجيه الشركة، أُلغي البند الخاص بوثيقة "١٥ - Claude Master Prompt" من قائمة التسليمات نهائيًا. تُعتبر كل الوثائق الرسمية (١٤ من أصل ١٤ متبقية بعد الإلغاء) وكل الموديولات السبعة مُسلَّمة بالكامل.
